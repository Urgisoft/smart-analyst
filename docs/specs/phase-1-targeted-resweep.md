## 1. Goal and exit gate

**Goal.** Re-run the parameter sweep on the **23 case_b cells** with the modern
worker so that schema-contamination artifacts collapse and each cell receives
an honest verdict: either case_a (genuine no-edge with full data) or — if any
have edge — a non-zero `gates_pass` row that becomes the project's first
survivor.

**Exit gate.** All three must hold for the affected cells:

1. `pct_data_span_zero` drops to `< 0.05` (was: variable, often > 0.5).
2. `pct_oos_sharpe_zero` drops to `< 0.05` (with same caveat).
3. The case_a/b/c heuristic re-classifies them out of `case_b_schema_contamination`.

If a cell still classifies as case_b after the re-sweep, it indicates a
deeper issue (worker bug, schema regression, ingest gap) — investigate
before declaring P1 done.

## 2. Inputs

### 2.1 The 23 case_b cells

Generated by the diagnostic SQL below. The SPEC documents the rule; the
list itself is generated when the SPEC is executed (cells may shift slightly
between writing the SPEC and running it, e.g., if a related sweep updated
some rows).

```sql
-- Diagnostic SQL: produce the case_b cell list for P1.
-- Runs against quantlab.strategy_scores FINAL joined with the bt_runs aggregate.
-- Output: one row per (strategy_type, tier, interval) cell flagged as case_b.
--
-- IMPORTANT: pct_data_span_zero / pct_oos_sharpe_zero use the FULL row count
-- (legacy + modern) as the denominator — that's what flags contamination.
-- But the case_c structural-limit exclusion uses MODERN-only rows
-- (modern_row_count = countIf(data_span_days > 0)). A cell with 12 legacy
-- rows + 8 modern rows must NOT survive the >= 16 gate as a case_b candidate;
-- it has only 8 honest data points and belongs in case_c.

WITH bt_agg AS (
    SELECT
        strategy_type,
        tier,
        interval,
        countIf(data_span_days = 0) / count()         AS pct_data_span_zero,
        countIf(oos_sharpe_ratio = 0) / count()       AS pct_oos_sharpe_zero,
        count()                                       AS row_count_total,
        countIf(data_span_days > 0)                   AS modern_row_count
    FROM quantlab.bt_runs
    GROUP BY strategy_type, tier, interval
)
SELECT
    s.strategy_type,
    s.tier,
    s.interval,
    s.wt_net_pct,
    s.gates_pass,
    a.pct_data_span_zero,
    a.pct_oos_sharpe_zero,
    a.row_count_total,
    a.modern_row_count
FROM quantlab.strategy_scores FINAL s
LEFT JOIN bt_agg a USING (strategy_type, tier, interval)
WHERE
    s.wt_net_pct > 0                          -- positive IS edge
    AND (
        a.pct_data_span_zero >= 0.20
     OR a.pct_oos_sharpe_zero >= 0.20
    )                                          -- schema-contamination flag
    AND a.modern_row_count >= 16               -- has enough HONEST data; not case_c
ORDER BY a.pct_data_span_zero DESC, s.strategy_type, s.tier, s.interval;
```

> **Threshold note.** The `0.20` contamination threshold and `wt_net_pct > 0`
> IS-edge filter are the heuristic boundaries that produced the original
> "23 case_b cells" count in the 2026-05-03 diagnostic. If the diagnostic
> output now diverges (22 / 24 / 25 cells), the run still proceeds — the
> divergence is logged in §6.4. If divergence is large (≥ 5 cells either
> way), pause and reconcile with the original diagnostic before sweeping.
>
> **bot.db caveat (ADR-005, `check.md` DI-03).** The re-sweep CLI does not
> filter `quantlab.candles` by `source`. Tokens with `source = 'botdb'`
> rows ARE included in the re-sweep universe — that's intentional, since
> the bot.db data is grandfathered and the case_b cells include some
> bot.db-backed tokens. Per-cell caveats are documented in §6.3 if any
> migrated cell becomes a survivor.

**Special-watch cell** that should be in the output:
`mean_reversion_v1 / mcap_micro / 1h` (226 tokens × 20 params, the largest cell).

**Excluded from re-sweep** (not eligible — see acceptance §6.4 for what to do
if these surface):

- `tsmom_vol_v1 / cex_major / 1d` — case_a, PBO=0.715. **BLOCKED**, not case_b.
- Any `wt_net_pct ≤ 0` cell (case_a_no_is_edge — 31 cells; honest fail).
- Any cell with `row_count < 16` (case_c structural-limit — 9 cells; bot.db caveat).

## 3. Procedure

### 3.1 Smoke run (gate before mass execution)

Run **one cell from the §2.1 diagnostic output** under the actual sweep CLI
to confirm the worker behavior is correct end-to-end. Pick the smallest cell
in the case_b set (lowest `modern_row_count`) — this minimises smoke wall-time
while exercising the same code path the mass run uses.

If the diagnostic output is not yet available, a defensible default is
`mean_reversion_v1 / mcap_nano / 1h` *if and only if* the diagnostic
confirms it is in the case_b set — otherwise the smoke run won't exercise
the contamination-collapse path, only the happy path.

**Use `npm run batch --` (raw CLI), not `npm run backtest --`** — verified
2026-05-03: `package.json` defines `batch` as `tsx scripts/batch_backtest.ts`
with no baked-in flags, while `backtest` bakes in
`--intervals 5m,15m,1h,1d --grid coarse --split-pct 70 --min-trades-persist 10
--min-token-history-days 90`. The flags below override safely under
`batch_backtest.ts`'s last-wins parsing rule (line 56-69), but `npm run batch`
is the correct alias to use because it composes more cleanly with the
per-cell scoping below.

```bash
npm run batch -- \
  --strategies mean_reversion_v1 \
  --tier mcap_nano \
  --intervals 1h \
  --grid coarse \
  --split-pct 70 \
  --min-trades-persist 10 \
  --min-token-history-days 90 \
  --force
```

**Smoke-pass criteria:**

- Wall-clock completes within 5× the cell's historical run time (sanity check
  against runaway threading).
- Inspect 5 random `bt_runs` rows from this sweep_id: every row has
  `data_span_days > 0` AND `oos_sharpe_ratio` populated (non-zero unless the
  param genuinely produced flat OOS).
- `npm run score:strategies` re-runs and the cell appears with
  `oos_is_status` set to one of the four valid enum values (not empty string).

**If smoke fails:** stop. The worker is not writing what HANDOFF claims.
Diagnose before proceeding.

### 3.2 Mass re-sweep

Group the 23 cells by `tier` to minimize the number of sweep invocations.
Each invocation hits one tier with all the strategies and intervals that
have case_b cells in that tier.

**Worked example.** Suppose the diagnostic outputs:

| strategy_type        | tier        | interval |
|----------------------|-------------|----------|
| mean_reversion_v1    | mcap_micro  | 1h       |
| momentum_v1          | mcap_micro  | 1h       |
| momentum_v1          | mcap_micro  | 4h       |
| mean_reversion_v1    | mcap_nano   | 1h       |
| ...                  | ...         | ...      |

Group by tier:

```bash
# Tier mcap_micro
npm run batch -- \
  --strategies mean_reversion_v1,momentum_v1 \
  --tier mcap_micro \
  --intervals 1h,4h \
  --grid coarse --split-pct 70 \
  --min-trades-persist 10 --min-token-history-days 90 \
  --force

# Tier mcap_nano
npm run batch -- \
  --strategies mean_reversion_v1 \
  --tier mcap_nano \
  --intervals 1h \
  --grid coarse --split-pct 70 \
  --min-trades-persist 10 --min-token-history-days 90 \
  --force

# … one invocation per tier, no more
```

**The `--force` flag is required** to bypass the 24h freshness cache. Without
it, the orchestrator will skip cells that ran recently (most case_b cells did).

### 3.3 Collision resolution (`ReplacingMergeTree`)

`bt_runs` is `ReplacingMergeTree` with a sort key including `sweep_id`.
The new sweep generates a fresh `sweep_id`, so new rows do **not** collide
with old rows — they coexist as separate parts. Old rows continue to exist
in `bt_runs` indefinitely; they are *not* collapsed by the new run.

`strategy_scores` is also `ReplacingMergeTree`, with `scored_at` as the
version column. After running `score:strategies`, the new rows shadow the
old ones on `FINAL` queries.

**Implication 1.** Querying without `FINAL` after the re-sweep will show old
case_b classification mixed with the new one. **Always use `FINAL` on
`strategy_scores`** in post-resweep diagnostics — `check.md` DI-02.

**Implication 2 — zombie row protection.** Because old `bt_runs` rows are
NOT removed, the diagnostic SQL in §2.1 must continue to filter
`pct_data_span_zero` correctly. The aggregation already does this: zero-span
rows from the legacy era stay in the denominator, and that's *intentional*
— it's how we measure contamination. The acceptance gate in §6.1 uses a
DIFFERENT computation that filters to modern rows only (see §3.5). The
two computations serve two purposes:

- **Diagnostic gate (input)** — uses full row count to flag contaminated cells.
- **Acceptance gate (output)** — uses modern-only count to verify post-sweep
  health.

This is intentional asymmetry. Do not "unify" them.

**Implication 3 — failed-run recovery.** If a tier's invocation fails partway
(F-2), the partial new sweep_id leaves rows in `bt_runs` that have
`data_span_days > 0` (modern format) — these are honest, just incomplete
coverage of the cell's tokens. Re-running the same tier produces a fresh
sweep_id; both partial and complete sweeps coexist. The acceptance gate
(§6.1, modern-only) sees both as good rows; the diagnostic SQL (§2.1, full
denominator) sees both as good. **No DELETE is required to recover.**
The only case requiring `ALTER TABLE … DELETE` is if a partial run
produced rows that *should* be considered defective (e.g., a worker bug
that wrote bad data with `data_span_days > 0`) — out of scope for this SPEC.

## 4. Runtime estimate

The 23 case_b cells span ~5 distinct (strategy, tier) pairs. Per HANDOFF,
case_b cells appear at intervals of `1h`, `4h`, and `1d` (5m / 15m do not
currently have case_b cells, but if the diagnostic surfaces any, expand
the estimate accordingly). With:

- **Coarse grid:** 7 params per cell.
- **Median tokens per cell:** ~50; the special-watch cell
  `mean_reversion_v1 / mcap_micro / 1h` has 226 tokens — that is the
  long-pole and dominates total wall time.
- **Median candles per token at 1h:** ~2000.
- **Worker pool:** `os.cpus().length - 2` threads (the user's 9950X box has
  16 cores → 14 worker threads).
- **Single-cell wall time** (estimated from prior runs):
  - 1h cells: 30–90s for ~50-token cells; up to 5–8 min for 226-token cell.
  - 4h cells: 20–60s (fewer candles per token).
  - 1d cells: 10–30s (much fewer candles per token).

**Total estimate:** 20–60 minutes wall on the user's 9950X / 64 GB RAM box,
dominated by the special-watch cell. The smoke run completes in under 2
minutes. The full mass re-sweep runs in one sitting; no checkpointing
needed. **If the run fails past minute 30:** consult §6.4 — the recovery
path uses re-invocation of the affected tier, not partial-row cleanup.

If 5m or 15m case_b cells surface in the diagnostic output, add 2–8 min
per cell to the estimate; flag if the total exceeds 90 min and consider
running 5m/15m cells as a separate pass.

## 5. Failure modes / what could break this

- **F-1.** Smoke run reveals worker still writing `data_span_days = 0` for
  some inserts. Means the 2026-05-02 fix is incomplete or regressed.
  Investigate `batch_backtest_worker.ts` insertion path before any mass run.
  *Check:* `check.md` DI-01.
- **F-2.** ClickHouse connection drops mid-sweep. Worker pool retries are
  enabled; on full failure, the `sweep_id` for that tier won't fully populate.
  Re-run that tier's invocation with `--force` to overwrite. (Idempotent because
  the new run gets a new `sweep_id`.)
- **F-3.** `--tier` filter excludes a token that had case_b rows in
  `bt_runs` from before its tier was reassigned. Highly unlikely (tier
  assignment is stable for cex_major/mcap_*), but if it surfaces,
  the affected cell will not improve. Diagnostic catches it (re-classification
  shows it still in case_b).
- **F-4.** A re-swept cell migrates to a non-zero `gates_pass` row — the
  first project survivor. Do **not** auto-promote; this is a Tier 1
  decision per MASTER §4.3. Required follow-ups:
  - Hit the validator at `http://localhost:3000/#/validator` with the
    surviving (strategy_type, tier, interval). The validator runs the four
    gates **independently** of `score_strategies` (per the lockstep
    discipline: same Sharpe / winner-pick logic, separate codepath that
    cross-checks the production scorer). Both must agree.
  - Re-deflate with an **independent N**: the user-facing N for DSR is the
    full param-trial count for the cell (per Bailey-LdP 2014), and the
    validator reads it directly from `bt_runs`. Confirm the validator
    output matches `strategy_scores.dsr_value` for the survivor row.
  - Write an ADR documenting the survivor: which cell, gate values, the
    binding-gate analysis. Then write a Phase 2 SPEC for cluster-tying.
  - **Forbidden:** `check.md` FB-04 (no live capital), `check.md` FB-02
    (no market switch), `check.md` FB-03 (no sweep without deflation —
    already satisfied here, listed for the reader). Per ADR-009, no
    cross-market work until P1 closes AND a survivor exists AND P2
    cluster-tying is done.
- **F-5.** A re-swept cell migrates to `case_a_no_edge` with
  PBO ≥ 0.5 — this is a *honest* fail. Do not retry, do not tweak params.
  *Forbidden* per MASTER §4.4 (PBO promotion).
- **F-6.** `--force` re-runs unaffected cells too if the strategy/tier/interval
  invocation overlaps. Mitigation: tightly-scoped invocations (one tier at
  a time, only the strategies / intervals with case_b in that tier).
  Cost: a few extra minutes if overlap is small. Acceptable.
- **F-7.** `oos_is_status` empty-string ghosts in `strategy_scores` if a
  query forgets `FINAL`. *Check:* `check.md` DI-02.

## 6. Acceptance criteria

### 6.1 Quantitative

- [ ] Smoke run: 5/5 sampled rows have `data_span_days > 0` and populated
      `oos_sharpe_ratio` (when the param genuinely produced any OOS trades —
      a flat-OOS row legitimately has `oos_sharpe_ratio = 0` with
      `data_span_days > 0`).
- [ ] Mass re-sweep completes without ClickHouse errors in the worker logs.
- [ ] `npm run score:strategies` re-runs and inserts ≥ 1 row per affected cell.
- [ ] **Modern-only acceptance gate.** Diagnostic SQL on
      `strategy_scores FINAL` joined with the modern-row aggregate shows,
      for each previously-affected cell:
      - `countIf(data_span_days = 0) / count()` calculated over rows
        with `sweep_id = <new_sweep_id>` is `< 0.05`.
      - `countIf(oos_sharpe_ratio = 0) / count()` calculated over rows
        with `sweep_id = <new_sweep_id>` AND `data_span_days > 0` AND
        `total_trades > 0` is `< 0.05` (excludes legitimate flat-OOS
        rows where the strategy traded but produced zero net OOS Sharpe;
        those are honest, not contamination).
- [ ] Affected cells re-classify out of `case_b_schema_contamination`.

> The modern-only acceptance gate filter is critical. The §2.1 diagnostic
> uses the full denominator to *flag* contamination; §6.1 uses a modern-row
> filter to *verify* the cell is now contamination-free. Mixing the two
> produces a false-fail when a legitimate flat-OOS run happens to land
> in the new sweep_id.

### 6.2 Test gate

- [ ] `npm test` still 383/383 (no regression in the deflation pipeline).
- [ ] `npx tsc --noEmit` clean.

### 6.3 Documentation gate

- [ ] HANDOFF rewritten with new cell counts in each class.
- [ ] MASTER.html §7 (living state) updated with new classification breakdown
      and verification stamp.
- [ ] If any cell migrates to a non-zero `gates_pass`, write a follow-up
      ADR documenting which cell and the verdict per gate.

### 6.4 What to do if exit gate fails

If the exit gate is NOT met:

- **Some cells still case_b after re-sweep:** investigate the worker's
  insertion path. Look for the specific `(strategy, tier, interval, token)`
  combinations where `data_span_days` is still 0 in the new sweep_id. This is
  a code bug; do not paper over.
- **All cells migrated but no survivors:** expected outcome. Document the
  new breakdown and proceed to Phase 2 SPEC.
- **A cell classifies as `case_a_no_edge` but the user wants to ship it:**
  refuse. Forbidden-list rule (PBO ≥ 0.5 promotion). Quote the binding gate.
