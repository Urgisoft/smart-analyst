1. System overview

SignalForge is a research lab for systematic crypto strategies. The thesis behind it is not "find the best strategy on Solana" — it is behavioral clustering across markets: assets cluster by their statistical properties (volatility, beta, liquidity, autocorrelation) regardless of their asset-class label, and a strategy that genuinely has edge on a behavioral cluster in one market should survive recalibration on the same cluster in a different market. Failing that survival test means the result was a venue-specific quirk, not a behavioral truth.

Everything else — the dashboard, the validator, the deflation pipeline, the broker abstraction yet to be built — exists to support that single research workflow without letting any of the well-known failure modes (selection bias, single-market overfit, undisciplined re-running, premature live capital) corrupt the conclusion.

The pipeline at a glance

Eight stages, one self-correction layer. Stages are serial; the self-correction layer runs across all of them. Rejection at any deflation gate sends work back to discovery — not to "try a different parameter range."

Why this exists

Almost everyone who tries systematic crypto trading produces beautiful in-sample results that disintegrate live. The reason is not that they are bad at coding — it is that they conflate "I tested 10,000 configurations and one looked great" with "I found edge." The first is the maximum of 10,000 random variables. The second requires deflation, walk-forward, and cross-market confirmation.

SignalForge is the local environment where every promotion decision passes through those gates. The headline result of the work to date — "0 of 69 cells pass all four gates" — is not a failure of the system; it is the system working. Most of those 0 are correctly being rejected. The next functional task (Phase 1 below) is fixing measurement artifacts in 23 of those cells so the rejection signal is honest.

North star
Confidence beats raw returns. A deflated Sharpe of 1.2 with PBO < 0.5 and cross-market confirmation beats a raw profit factor of 3 from a single market sweep, every time. The system is built around this preference; every gate exists to enforce it.
Where ML clustering fits — and why it's P2, not P1
The canonical research pipeline (per quant_reference.html) puts ML clustering as stage 1, upstream of strategy design. SignalForge has it historically inverted — existing strategies were designed first, then applied to static tier slices (vol_high, mcap_micro, etc.). Those tiers are a coarse approximation of behavioral clusters (they use 3 of the 4 canonical features: vol, β, mcap; the missing one is autocorrelation), but they're static buckets with frozen membership. Phase 2 closes both gaps: continuous feature-space clustering with weekly-recomputed membership.

The reason clustering stays P2 (not P1) is the binding bottleneck. The "0 of 69 cells pass" headline is measurement artifact, not strategy failure — the 23 case_b cells have schema contamination. Re-defining the universe before fixing the metric that grades strategies on it produces a fancier-looking "0 of N" headline, not progress. P1 unblocks the signal; P2 upgrades the universe; together they let us ask the right question. For new strategies (post-P5), the canonical order applies: cluster first, then design.

Drift signal
The user has flagged three specific drift patterns: (a) jumping to ML when the primary pipeline isn't producing survivors, (b) switching markets to escape a validation problem, (c) building multi-agent orchestration as a substitute for finishing concrete work. 4. Self-correction layer

The single most important addition to the system. The 2026-05-03 framing-error incident — where "unscorable" silently conflated "no IS edge" with "data missing" — is the canonical example of a class of error that no test catches because the test passes against the wrong question. The self-correction layer's purpose is to catch that class of error.

The four mechanisms

The four mechanisms operate at different points. check.md is what the producer applies; the critic agent is what catches things the producer missed; tier checkpoints decide whether the user sees it; the forbidden list refuses certain things up front.

4.1 The check.md system

check.md is a growing checklist of self-correction prompts. Every entry is a question or invariant that, if violated silently, produces silent corruption of the research result. Status as of this document: the seed entries below are committed inline here only — check.md is not yet a file at the repo root. Phase 0 task: extract the 40 entries below into check.md and pin a counter at the top. Until that ships, this document's §4.1 is the authoritative version.

Initial seed (40 entries — full file produced at Phase 0). Snapshot of the structure:

FRAMING (the 2026-05-03 incident class)

FR-01Before producing a diagnostic, list the symptom-vs-cause distinction explicitly. What is the binding mechanism, and have I verified it with a query before writing the fix?
FR-02Does any sentinel value (zero, empty string, null) collapse multiple distinct conditions into one bucket? If so, name them before proceeding.
FR-03If the user said "X is wrong", have I checked whether my framing of X is wrong, not just my answer? Wrong question → right-shaped answer → silent error.

STATISTICS (deflation correctness)

ST-01For DSR: is N (trial count) the actual number of param trials, not the number of cells or the number of strategies?
ST-02aFor PSR at strategy-level (cross-cell ranking, applyLeaderboardHaircut input): nObservations is trade count (Bailey-LdP 2014, §2 — Sharpe SE under iid trades). The codebase passes totalTrades here.
ST-02bFor HLZ T (validator-cell path, time-series Sharpe): T = data_span_days × bars_per_day — bars, not trades. The two paths use different denominators by design; do not unify them. Existing inconsistency is intentional but easy to misread; flag in code review.
ST-03For HLZ: is the t-stat I'm correcting derived from a Sharpe whose underlying assumptions (iid, normal, mean-known) are checked?
ST-04For PBO via CSCV: are the splits actually independent, or do overlapping windows leak?
ST-05Have I tested on a positive control (synthetic data where the answer is known)?

BACKTEST DESIGN

BT-01Is the cost model (fees + slippage + funding) honest for the venue, or am I assuming zero?
BT-02Is the IS/OOS split done before the param sweep, or am I peeking?
BT-03Are tokens with < 90 days of history excluded? Survivorship bias is the silent killer.
BT-04Does the engine close positions at bar-close or bar-open? Mismatch produces phantom edge.
BT-05Are walk-forward windows non-overlapping, or do I have look-ahead leakage?
BT-06For cross-sectional strategies, is the rebalance schedule realistic (cost-aware), not assumed-instant?

DATA INTEGRITY

DI-01Are bt_runs rows from before/after a schema migration mixed in this query? data_span_days > 0 is the modern-row filter.
DI-02Does this query use FINAL on ReplacingMergeTree tables? Without it I see pre-merge ghosts.
DI-03For bot.db-sourced rows (source = 'botdb'): is the cost-model caveat applied per ADR-005?
DI-04Have I verified my count by joining the source table, not just trusting the aggregate?

METHODOLOGY

ME-01Have I cited the source for any non-trivial statistical choice (book + chapter, or paper + section)?
ME-02Am I about to invent a citation? If unsure, say "I recall a result like this but can't verify."
ME-03Is this a Tier-3 source? If so, did I disclose it?
ME-04Does any Tier-1 source actively not apply here (e.g., assumes equity, doesn't translate to 24/7 crypto)? If so, did I flag it?

USER-COLLABORATION

UC-01Am I about to skip a stage (RESEARCH → DESIGN → SPEC → CODE)? Refuse and name what's unresolved.
UC-02Am I assuming user buy-in on a methodology choice without naming the alternatives?
UC-03Did the user use a term incorrectly? Correct it briefly, with the source.
UC-04Is this a load-bearing concept? Use the [TEACH] role: intuition → mechanism → failure mode.
UC-05Drift signal: is the user proposing ML / market-switch / multi-agent as a substitute for finishing the current concrete task? Name the pattern.

CODE

CO-01Did I use an existing battle-tested library (technicalindicators, scipy, statsmodels), or am I reimplementing?
CO-02Are silent dependencies (env var, CH table, upstream function) called out at the top of the diff?
CO-03Did I add tests for the edge cases the spec named, not just the happy path?
CO-04Type-check pass: npx tsc --noEmit clean?
CO-05Test-suite pass: npm test green?

4.2 The critic agent

The critic agent is a separate Claude invocation (via the Claude Code Agent tool with subagent_type appropriate to the artifact: code-reviewer for diffs, general-purpose for analysis docs). The critic does not see the producer's reasoning — only the artifact. Its job is to apply check.md against what was produced and report violations.

When it runs: automatically before any artifact is presented to the user that touches:

  • A new ADR (commitment 2)
  • A SPEC document (Vector Core SPEC stage)
  • A diff that touches deflation code (src/lib/psr.ts, src/lib/cscv.ts, src/lib/hlzHaircut.ts, scripts/score_strategies.ts, src/lib/validator*.ts)
  • A schema migration
  • The MASTER document itself (this file)

Researcher and test-generator agents are siblings of the critic. The researcher is invoked when the producer has cited a paper or method but is uncertain about a specific claim — it does literature lookup against the canon. The test-generator is invoked when a new SPEC has named edge cases — it produces unit tests covering each before the CODE stage begins.

4.4 Forbidden list

Codified actions that are refused regardless of how they are asked, with the canonical reason. PUSHBACK references this list rather than re-deriving the rule each time.

Add a new strategy to the registry while the existing pipeline has zero survivors. Reason: more strategies inflate the multiple-testing burden without addressing the bottleneck (which is data quality / cell evaluation), and dilute attention. Unblock when: ≥ 1 cell passes all four gates AND survives a cross-market check.
Switch the primary market to escape a validation problem. Reason: the cross-market protocol is "transfer hypothesis after local survival", not "give up locally and try elsewhere." Switching pre-survival defeats the validation purpose. Unblock when: a cell has survived locally; switch is then a phase-4 cross-market run, not a primary-market change.
Run a parameter sweep without applying deflation (DSR + PBO + HLZ). Reason: the maximum of N random trials is not edge. Reporting raw best-of-N is misleading by construction. Unblock when: never. Even diagnostic sweeps must produce deflated metrics for the surviving rows.
Deploy live capital before paper-trade evidence. Reason: backtests are hypothesis tests, not forecasts; paper trade reveals execution-model assumptions. Unblock when: ≥ N weeks of paper-trade data with realized-vs-backtest divergence within tolerance (N defined at Phase 6 SPEC).
Skip a Vector Core stage (RESEARCH → DESIGN → SPEC → CODE). Reason: stage skips are how silent corruption enters; "let's just code it" is the most common drift. Unblock when: never. If the spec exposes a hole, kick back to RESEARCH; do not paper over.
Re-implement what a battle-tested library already does (DSR formula reinvention, custom RSI, hand-rolled CSV parser). Reason: reimplementation is bug-prone and overfit-prone. Unblock when: a specific, named library deficiency is documented in an ADR.
Invent a citation. Reason: Vector Core canon, no exceptions. If unsure, say "I recall a result like this but can't verify the source." Unblock when: never.
Run a destructive operation (ALTER TABLE … DELETE, schema rollback, force-push) without rewriting the handoff first. Reason: if the destruction goes wrong, the prior state is the only recovery path. Unblock when: handoff written, last-updated date current, user signed off if Tier 1.
Promote a cell with PBO ≥ 0.5 because DSR is high. Reason: PBO > 0.5 means the selection mechanism is anti-correlated with OOS — high IS DSR is the symptom, not a counter-argument. Unblock when: never. (See: tsmom_vol_v1 / cex_major / 1d, the canary.)

  • Cluster statistics are stable; cluster membership recomputed weekly.

Status: infrastructure shipped (per the Behavioral clustering stack table in §3); exit gate not met because Phase 1 produced 0 surviving cells. 9. Anti-hallucination protocol

The risk is concrete and grows with context length: as a session fills, the producer (Claude) starts mis-remembering decisions, file paths, test counts, schema details. Errors compound silently because the producer doesn't notice it's drifting — the recalled fact feels as confident as the verified fact. This part codifies defenses. It is not optional.

The failure mode being defended against
"I remember we decided X" → confident edit based on X → X was actually Y, decided three sessions ago → silent corruption that no test catches because the test was written against X too. The 2026-05-03 framing-error incident was a less severe version of this same class.

Three layers of defense

Three layers, each catching a different drift mode. L1 is per-action discipline; L2 is independent review; L3 is periodic re-grounding. None is sufficient alone.

9.1 Refuse rules (hard)

The producer must refuse the following actions even if asked, until the rule is satisfied:

Claim "tests pass" / "lint clean" / "type-check passes" without running the verification this turn. Unblock: run the command and quote the output.
Edit a file from recall (without a Read in this turn). Unblock: Read the file just before the Edit. The Edit tool already enforces this; the rule is to not work around it.
Restate an ADR's decision from memory in a new ADR or in a code comment. Unblock: read the ADR file and quote the decision verbatim.
Run a destructive operation (schema migration, force push, large DELETE, OPTIMIZE FINAL on a hot table) without re-reading both MASTER §7 (living state) and the relevant component file in the same turn. Unblock: read both, present diff for confirmation if Tier 1.
Introduce a domain term not in MASTER §8 glossary. Unblock: add the term to the glossary in the same turn, with a one-line definition.
Continue a session past 50 turns of dense work without writing HANDOFF and offering to /clear. Unblock: write HANDOFF (the protocol triggers anyway); recommend /clear and a fresh session for the next chunk of work.

9.2 Verification stamps

When stating a fact about state — test counts, row counts, file paths, dependency versions, schema columns — include the date the fact was last verified, in the form (verified 2026-05-03). Stale stamps are not lies, but they signal the reader to check before acting.

Example:

BAD:  "The strategy_scores table has the oos_is_status column."
GOOD: "strategy_scores has oos_is_status (LowCardinality(String), DEFAULT '')
       — verified in scripts/score_strategies.ts schema, 2026-05-03."

9.3 Anchor checks at session start

Before producing any work in a fresh session, the producer reads — in this order — and confirms internally that nothing in the current task contradicts:

  1. .claude/HANDOFF.md — auto-loaded. Captures last-session state.
  2. MASTER.html §7 — living state. May contain newer info than HANDOFF if HANDOFF wasn't rewritten.
  3. check.md — the procedural memory. Scan for relevant domains.
  4. docs/decisions/ last 3 ADRs — recent decisions most likely to bear on the active task.
  5. Component file(s) directly affected by the active task — never trust recall on file structure.

This is roughly 5 reads, ~3-5k tokens. It's the cheapest insurance against drift.

9.4 Mid-session anchors

Every ~30 turns, or before any Tier 1 action, the producer re-reads MASTER §7. The act of re-reading is itself the defense — it surfaces the cases where chat memory has drifted from file truth. If a contradiction surfaces, write the HANDOFF and consider /clear.

9.5 Critic-agent role in drift defense

The critic agent is the strongest single defense because it has no chat context. It cannot inherit the producer's drift. The producer's job is to invoke it on the artifacts that matter most — and trust its findings even when they contradict the producer's recall.

Critic invocation, in order of strength:

  1. Architectural artifacts (MASTER edits, new SPECs, new ADRs) — critic required.
  2. Deflation-pipeline diffs (psr.ts, cscv.ts, hlzHaircut.ts, score_strategies.ts, validator*.ts) — critic required.
  3. Schema migrations — critic required.
  4. Other diffs > 100 lines — critic recommended; producer's call.

9.6 What the user should watch for

The producer's own drift defenses miss things by definition. The user is the third line. Patterns that signal drift:

  • The producer cites a file path or function name with no Read tool call this session.
  • The producer states a test count, row count, or schema fact without a verification stamp or recent run.
  • The producer describes "what we decided" without quoting the ADR.
  • The producer's plan reference Phase numbers or component names that don't appear in MASTER §3 or §5.
  • The producer answers "how does X work?" with confidence but no Read tool call to the X file.

If you spot any of these, the right response is "verify that against the file" or "quote the ADR." The producer will course-correct.
